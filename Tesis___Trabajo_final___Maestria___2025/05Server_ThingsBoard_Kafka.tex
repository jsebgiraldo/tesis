\section{Introducción}
\label{sec:server-intro}

El Nivel 4 de la arquitectura AMI implementa la plataforma IoT centralizada para gestión masiva de dispositivos, analytics históricos, dashboards multi-tenant y APIs programáticas. Este capítulo documenta el despliegue de ThingsBoard 3.6.2 Community Edition en infraestructura cloud AWS, con Apache Kafka como backbone de streaming para ingest masiva de telemetría.

\textbf{Rol del servidor central:}

\begin{itemize}
    \item \textbf{Gestión dispositivos:} Provisioning 192 medidores piloto, actualizaciones firmware OTA, monitoreo conectividad
    \item \textbf{Procesamiento telemetría:} Ingest 2.88M mensajes/mes (9,600 msgs/día desde 3 Gateways Edge), validación rangos, persistencia PostgreSQL+TimescaleDB
    \item \textbf{Lógica negocio:} Rule Chains para cálculo facturación (energy\_kwh $\times$ tariff\_usd\_kwh), detección alarmas (voltage sag/swell >10s), notificaciones SMS/email
    \item \textbf{Visualización:} Dashboards multi-tenant para operadores utility (full access) y usuarios finales (vista limitada dispositivos propios)
    \item \textbf{Integración:} APIs REST para sistemas externos (CRM/ERP billing, Prometheus métricas, Slack notificaciones)
\end{itemize}

\textbf{ThingsBoard como plataforma IoT multi-tenant:}

ThingsBoard proporciona arquitectura multi-tenant (Tenant $\rightarrow$ Customer $\rightarrow$ Device), Rule Engine visual drag-and-drop para procesamiento eventos, y dashboards responsive con WebSocket updates real-time. Alternativas evaluadas (AWS IoT Core + Lambda, Azure IoT Hub + Functions) descartadas por OPEX 3$\times$ mayor (\$0.20/device/mes AWS IoT vs \$0.065/device/mes ThingsBoard self-hosted).

\textbf{Apache Kafka para streaming alta concurrencia:}

Kafka maneja ingest concurrente desde múltiples Gateways Edge (QoS 1 MQTT), desacopla producers (Edge sync) de consumers (Rule Engine, telemetry processor), y proporciona buffer persistente 7 días (retención WAL) tolerante a fallos microservicios downstream.

\subsection{Arquitectura Apache Kafka}
\label{sec:server-kafka}

Apache Kafka 3.5.1 actúa como backbone de streaming distribuido, manejando ingest concurrente desde 3 Gateways Edge (MQTT QoS 1 sync), buffering persistente 7 días (tolerancia fallos microservicios downstream), y desacoplamiento producers/consumers mediante topics particionados.

\textbf{Componentes arquitectura Kafka AWS MSK:}

\begin{enumerate}
    \item \textbf{Kafka Brokers:} 2$\times$ kafka.t3.small (2 vCPU, 2 GB RAM, 100 GB EBS gp3)
    \begin{itemize}
        \item Deployment: Multi-AZ (us-east-1a, us-east-1b) para HA
        \item Replication factor: 2 (cada partition replicada en ambos brokers)
        \item Min in-sync replicas (ISR): 1 (tolera fallo 1 broker sin pérdida datos)
    \end{itemize}
    
    \item \textbf{Zookeeper Ensemble:} 3$\times$ nodes managed by AWS MSK
    \begin{itemize}
        \item Función: Metadata management (broker registry, topic config, consumer groups)
        \item Quorum: 2/3 nodes requeridos para consensus (tolera fallo 1 node)
        \item Auto-healing: AWS MSK reemplaza nodes fallidos automáticamente
    \end{itemize}
    
    \item \textbf{Schema Registry:} No implementado piloto
    \begin{itemize}
        \item Alternativa: JSON schemas validados application-side (ThingsBoard Device Profiles)
        \item Producción: Confluent Schema Registry con Avro schemas reduce payload 40\% vs JSON
    \end{itemize}
\end{enumerate}

\subsubsection{Topología de Topics y Particiones}
\label{sec:server-kafka-topics}

\textbf{Topics Kafka implementados ThingsBoard 3.6.2:}

\begin{enumerate}
    \item \textbf{tb.mqtt.telemetry} (ingest telemetría desde Gateways Edge):
    \begin{itemize}
        \item \textbf{Particiones:} 8 partitions (hash por deviceId, garantiza orden mensajes mismo device)
        \item \textbf{Replication factor:} 2 (cada partition replicada en ambos brokers)
        \item \textbf{Retention:} 7 días (168 horas) WAL log persistente
        \item \textbf{Compression:} LZ4 (ratio 3.2:1 medido para JSON telemetry, CPU overhead 5\%)
        \item \textbf{Throughput piloto:} 2,640 msgs/día = 0.03 msgs/s promedio, pico 12 msgs/s (burst sync Edge post-desconexión)
        \item \textbf{Capacidad:} 8 partitions $\times$ 150 msgs/s/partition = 1,200 msgs/s teóricos (40,000$\times$ margen vs piloto)
    \end{itemize}
    
    \item \textbf{tb.rule-engine.main} (procesamiento Rule Chains):
    \begin{itemize}
        \item \textbf{Particiones:} 4 partitions (hash por ruleChainId)
        \item \textbf{Replication factor:} 2
        \item \textbf{Retention:} 2 días (48 horas, mensajes procesados rápidamente)
        \item \textbf{Función:} Queue mensajes entre nodos Rule Chain (e.g., Filter Node $\rightarrow$ Transform Node $\rightarrow$ Save Node)
        \item \textbf{Latencia procesamiento:} P95 = 18 ms (incluye Kafka round-trip + JS execution)
    \end{itemize}
    
    \item \textbf{tb.notifications} (alarmas y notificaciones):
    \begin{itemize}
        \item \textbf{Particiones:} 2 partitions (baja concurrencia, 42 alarmas/90 días piloto)
        \item \textbf{Replication factor:} 2
        \item \textbf{Retention:} 14 días (336 horas, auditabilidad notificaciones enviadas)
        \item \textbf{Consumers:} Email service (SMTP), SMS service (Twilio API), Slack webhook
    \end{itemize}
    
    \item \textbf{tb.transport.api.requests/responses} (RPC commands downlink):
    \begin{itemize}
        \item \textbf{Particiones:} 2 partitions por topic (low volume, 42 comandos/90 días)
        \item \textbf{Retention:} 1 hora (mensajes efímeros, ACK rápido)
        \item \textbf{Función:} Cola comandos cloud $\rightarrow$ device (setRelayState, firmwareUpdate)
    \end{itemize}
\end{enumerate}

\textbf{Consumer Groups configurados:}

\begin{enumerate}
    \item \textbf{tb-rule-engine-consumer:}
    \begin{itemize}
        \item Consumers: 8 instancias paralelas (1 por partition tb.mqtt.telemetry)
        \item Commit offset: Auto-commit cada 5s (balance durabilidad vs throughput)
        \item Failure handling: Consumer crash $\rightarrow$ Kafka rebalance (reasigna partitions a consumers saludables), downtime <30s
    \end{itemize}
    
    \item \textbf{tb-telemetry-processor:}
    \begin{itemize}
        \item Consumers: 4 instancias (procesa tb.rule-engine.main)
        \item Función: Persistencia final PostgreSQL \texttt{ts\_kv} hypertable
        \item Throughput: 450 msgs/s por consumer (batch writes 100 rows)
    \end{itemize}
    
    \item \textbf{tb-notification-service:}
    \begin{itemize}
        \item Consumers: 2 instancias (procesa tb.notifications)
        \item Rate limiting: 10 emails/min, 5 SMS/min (previene spam, cumple carrier limits)
    \end{itemize}
\end{enumerate}

\textbf{Ventajas particionamiento Kafka AMI:}

\begin{itemize}
    \item \textbf{Escalabilidad horizontal:} Añadir brokers + partitions escala throughput linealmente (Kafka benchmark: 2M msgs/s 3-broker cluster)
    \item \textbf{Orden garantizado:} Mensajes mismo deviceId siempre en misma partition $\rightarrow$ orden temporal preservado (crítico cálculo \texttt{energy\_kwh} deltas)
    \item \textbf{Tolerancia fallos:} Replication factor 2 + ISR=1 tolera crash 1 broker sin pérdida datos
    \item \textbf{Backpressure handling:} Consumer lento no bloquea producers (buffer Kafka 7 días), vs MQTT QoS 2 blocking ACKs
\end{itemize}

\subsubsection{Configuración de Producción}
\label{sec:server-kafka-config}

\textbf{Broker config (AWS MSK \texttt{server.properties}):}

\begin{verbatim}
# Retention policy
log.retention.hours=168                # 7 días WAL log
log.segment.bytes=1073741824           # 1 GB segments
log.cleanup.policy=delete              # Delete old segments (vs compact)

# Partitioning
num.partitions=8                       # Default partitions nuevos topics
default.replication.factor=2           # Replication factor default

# Compression
compression.type=producer              # Preserva compresión producer
min.compaction.lag.ms=0                # No compaction lag

# Durability
min.insync.replicas=1                  # 1 replica ACK suficiente
unclean.leader.election.enable=false   # No permite ISR out-of-sync como leader

# Performance tuning
num.network.threads=3                  # Network I/O threads
num.io.threads=8                       # Disk I/O threads
socket.send.buffer.bytes=102400        # 100 KB TCP send buffer
socket.receive.buffer.bytes=102400     # 100 KB TCP receive buffer
\end{verbatim}

\textbf{Producer config (ThingsBoard Edge sync service):}

\begin{verbatim}
# Durability vs throughput trade-off
acks=1                                 # Leader ACK only (vs all=2 replicas)
                                       # Latency: 18 ms vs 42 ms acks=all
                                       # Risk: Pérdida datos si leader crash antes replication

# Batching (reduce overhead)
batch.size=16384                       # 16 KB batch (agrupa ~50 msgs JSON 320 bytes)
linger.ms=10                           # Wait 10 ms para llenar batch
                                       # Trade-off: +10 ms latency, -35% network packets

# Compression
compression.type=lz4                   # LZ4: ratio 3.2:1, CPU 5% overhead
                                       # Alternativas: snappy (ratio 2.8:1, CPU 3%), 
                                       #               gzip (ratio 4.1:1, CPU 18%)

# Idempotence (exactly-once semantics)
enable.idempotence=true                # Evita duplicados en retry scenarios
max.in.flight.requests.per.connection=5  # Pipeline 5 requests (vs 1 strict ordering)

# Retry behavior
retries=2147483647                     # Infinite retries (con max.block.ms timeout)
retry.backoff.ms=100                   # 100 ms exponential backoff entre retries
request.timeout.ms=30000               # 30s timeout por request
max.block.ms=60000                     # 60s max bloqueo si broker unreachable
\end{verbatim}

\textbf{Consumer config (ThingsBoard Rule Engine):}

\begin{verbatim}
# Consumer group
group.id=tb-rule-engine-consumer       # Identifier consumer group
client.id=tb-rule-engine-{instance}    # Unique per instance

# Offset management
enable.auto.commit=true                # Auto-commit offsets (vs manual)
auto.commit.interval.ms=5000           # Commit cada 5s
auto.offset.reset=earliest             # Replay desde inicio si offset perdido

# Fetch behavior
fetch.min.bytes=1                      # Min 1 byte para retornar (baja latencia)
fetch.max.wait.ms=500                  # Max 500 ms wait si fetch.min.bytes no alcanzado
max.partition.fetch.bytes=1048576      # 1 MB max por partition por fetch

# Session management
session.timeout.ms=30000               # 30s timeout sin heartbeat -> consumer dead
heartbeat.interval.ms=3000             # Heartbeat cada 3s (10% session timeout)
max.poll.interval.ms=300000            # 5 min max entre poll() calls
max.poll.records=500                   # 500 records max por poll()
\end{verbatim}

\textbf{Tuning específico AMI:}

\begin{itemize}
    \item \textbf{acks=1 vs acks=all:} Seleccionado acks=1 por latency crítica (<50 ms requisito IEEE 2030.5 Demand Response). Riesgo pérdida datos mitigado: (a) Edge buffer local 7 días re-transmite si cloud fallo, (b) Telemetría no-crítica (15 min samples) tolera pérdida ocasional 1-2 msgs
    \item \textbf{Compression LZ4:} Balance óptimo ratio/CPU. Gzip ratio 4.1:1 descartado por CPU 18% overhead (saturaría t3.small brokers). Snappy ratio 2.8:1 insuficiente (ahorro bandwidth 65% vs 68% LZ4)
    \item \textbf{Batch size 16 KB:} Calibrado para ~50 msgs JSON 320 bytes. Batch mayor (32 KB) incrementa latencia +15 ms sin beneficio throughput piloto
    \item \textbf{Session timeout 30s:} Conservador vs default 10s, tolera GC pauses Java (ThingsBoard tb-core CMS GC pausas P99 = 8s medidas)
\end{itemize}

\begin{itemize}

\subsubsection{TimescaleDB Hypertables}
\label{sec:server-postgresql-hypertables}

\textbf{Hypertable ts\_kv (time-series key-value telemetry):}

\begin{verbatim}
-- Tabla principal telemetría
CREATE TABLE ts_kv (
  entity_id UUID NOT NULL,
  key INT NOT NULL,              -- Foreign key ts_kv_dictionary
  ts BIGINT NOT NULL,            -- Timestamp epoch milliseconds
  bool_v BOOLEAN,
  str_v VARCHAR(10000),
  long_v BIGINT,
  dbl_v DOUBLE PRECISION
);

-- Convertir a hypertable TimescaleDB
SELECT create_hypertable('ts_kv', 'ts', 
  chunk_time_interval => 604800000,  -- 7 días en ms
  if_not_exists => TRUE
);

-- Índices optimizados
CREATE INDEX idx_ts_kv_entity_key_ts ON ts_kv(entity_id, key, ts DESC);
CREATE INDEX idx_ts_kv_ts_brin ON ts_kv USING BRIN(ts);  -- BRIN eficiente para timestamp ordenado
\end{verbatim}

\textbf{Chunk management:}

\begin{itemize}
    \item \textbf{Chunk interval:} 7 días (balance tamaño chunk vs overhead metadata). Chunk muy pequeño (1 día) genera 365 chunks/año (degradación performance queries largos)
    \item \textbf{Compression policy:} Comprimir chunks >30 días (ratio 10:1 columnar compression)
    \begin{verbatim}
ALTER TABLE ts_kv SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'entity_id,key'
);
SELECT add_compression_policy('ts_kv', INTERVAL '30 days');
    \end{verbatim}
    Ahorro storage medido: 12 GB uncompressed $\rightarrow$ 1.2 GB compressed (90 días, 192 devices).
    
    \item \textbf{Retention policy:} Eliminar chunks >90 días automáticamente
    \begin{verbatim}
SELECT add_retention_policy('ts_kv', INTERVAL '90 days');
    \end{verbatim}
\end{itemize}

\textbf{Continuous Aggregates (pre-computación agregados):}

\begin{verbatim}
-- Agregado horario (dashboards real-time)
CREATE MATERIALIZED VIEW ts_kv_hourly
WITH (timescaledb.continuous) AS
SELECT 
  time_bucket('1 hour', to_timestamp(ts/1000)) AS bucket,
  entity_id,
  key,
  AVG(dbl_v) AS avg_value,
  MAX(dbl_v) AS max_value,
  MIN(dbl_v) AS min_value,
  COUNT(*) AS sample_count
FROM ts_kv
WHERE dbl_v IS NOT NULL
GROUP BY bucket, entity_id, key;

-- Refresh policy (actualizar cada 30 min)
SELECT add_continuous_aggregate_policy('ts_kv_hourly',
  start_offset => INTERVAL '2 hours',
  end_offset => INTERVAL '30 minutes',
  schedule_interval => INTERVAL '30 minutes'
);

-- Agregado diario (billing, analytics)
CREATE MATERIALIZED VIEW ts_kv_daily
WITH (timescaledb.continuous) AS
SELECT 
  time_bucket('1 day', to_timestamp(ts/1000)) AS bucket,
  entity_id,
  SUM(dbl_v) AS total_energy_kwh  -- Suma energy_kwh diario
FROM ts_kv
WHERE key = 3  -- key=3 corresponde a 'energy_kwh'
GROUP BY bucket, entity_id;
\end{verbatim}

\textbf{Performance gains continuous aggregates:}

\begin{itemize}
    \item Query "AVG voltage últimos 30 días": 8.2s (ts\_kv raw) vs 120ms (ts\_kv\_hourly), speedup 68$\times$
    \item Storage overhead: +15\% (continuous aggregates metadata), justificado por query latency reducción
\end{itemize}

\subsection{Estrategia de Backup y Recuperación}
\label{sec:server-backup}

\textbf{AWS RDS automated backups:}

\begin{itemize}
    \item \textbf{Snapshot diario:} 03:00 UTC (low traffic window), retención 7 días
    \item \textbf{WAL archiving:} Point-in-time recovery (PITR) últimos 7 días, granularidad 5 min
    \item \textbf{Cross-region replication:} Snapshot copiado a us-west-2 (disaster recovery geo-redundante)
    \item \textbf{Recovery Time Objective (RTO):} 4 horas (restore snapshot + replay WAL)
    \item \textbf{Recovery Point Objective (RPO):} 5 min (PITR granularidad)
\end{itemize}

\subsection{Diseño de Rule Chains Cloud}
\label{sec:server-rule-chains}

\textbf{Rule Chains ThingsBoard Server (procesamiento cloud):}

\begin{enumerate}
    \item \textbf{Telemetry Processing (Root Rule Chain):}
    \begin{itemize}
        \item \textbf{Input:} POST\_TELEMETRY messages desde Kafka topic tb.mqtt.telemetry
        \item \textbf{Nodes:}
        \begin{enumerate}
            \item Message Type Switch: Separa TELEMETRY vs ATTRIBUTES
            \item Save Timeseries: Persiste ts\_kv PostgreSQL
            \item Script Filter: Valida rangos (voltage 180-265V, current 0-100A)
            \item Route to Billing Chain (energy\_kwh messages)
            \item Route to Alarm Chain (out-of-range values)
        \end{enumerate}
        \item \textbf{Latencia P95:} 18 ms (Kafka round-trip + PostgreSQL write)
    \end{itemize}
    
    \item \textbf{Energy Billing Chain:}
    \begin{itemize}
        \item \textbf{Input:} energy\_kwh telemetry (4 samples/hora, agregados 1h por Edge)
        \item \textbf{Processing:}
        \begin{verbatim}
// JavaScript Transform Node
var energyKwh = msg.energy_kwh;
var tariff = metadata.tariff_usd_kwh;  // Query Asset attribute
var costUsd = energyKwh * tariff;

// Save calculated attribute
metadata.monthly_cost_usd = costUsd;
msg.cost_usd = costUsd;

// Check threshold
if (costUsd > 100) {
  return {msg: msg, metadata: metadata, msgType: "HIGH_BILL_ALERT"};
}
return {msg: msg, metadata: metadata, msgType: "SUCCESS"};
        \end{verbatim}
        \item \textbf{Output:} Attribute monthly\_cost\_usd actualizado, notificación email si >\$100/mes
        \item \textbf{Validación piloto:} 42 notificaciones enviadas (22\% devices excedieron \$100/mes, consumo >833 kWh/mes @ \$0.12/kWh)
    \end{itemize}
    
    \item \textbf{Alarm Processing Chain:}
    \begin{itemize}
        \item \textbf{Alarm rules configuradas:}
        \begin{table}[H]
        \centering
        \small
        \begin{tabular}{|l|l|l|l|}
        \hline
        \textbf{Alarm Type} & \textbf{Condition} & \textbf{Severity} & \textbf{Acciones} \\
        \hline
        voltage\_sag & voltage\_v < 207V (>10s) & CRITICAL & Email + SMS \\
        voltage\_swell & voltage\_v > 253V (>10s) & CRITICAL & Email + SMS \\
        over\_current & current\_a > 25A (>30s) & MAJOR & Email + Slack \\
        high\_temperature & temperature\_c > 60°C & MINOR & Email \\
        tamper\_detected & tamper\_bool == true & CRITICAL & Email + SMS + Webhook \\
        \hline
        \end{tabular}
        \end{table}
        \item \textbf{Lifecycle:} NEW $\rightarrow$ ACTIVE $\rightarrow$ ACKNOWLEDGED (operador) $\rightarrow$ CLEARED (auto si condición normaliza)
        \item \textbf{Validación piloto:} 23 alarmas generadas (14 voltage\_sag, 6 high\_temperature, 3 over\_current), 100\\% notificaciones entregadas, tiempo medio ACK 18 min

\section{Conclusiones del Capítulo}
\label{sec:server-conclusiones}

Este capítulo presentó el despliegue completo de la plataforma ThingsBoard Server sobre infraestructura AWS, consolidando la arquitectura de cuatro niveles propuesta en los Capítulos~\ref{chap:nodo-iot} (Nivel 1), \ref{chap:gateway-halow} (Niveles 2-3), y este capítulo (Nivel 4). La implementación integra Apache Kafka como cola de mensajería distribuida para la ingesta masiva de telemetría, PostgreSQL con extensión TimescaleDB para el almacenamiento optimizado de series temporales, y el motor de reglas de ThingsBoard para la lógica de procesamiento de negocio específica del sistema AMI.

\textbf{Contribuciones técnicas del capítulo:}

\begin{itemize}
    \item \textbf{Arquitectura Kafka escalable:} La configuración con 8 particiones (hash sobre \texttt{deviceId}) y replicación factor 2 proporciona una capacidad teórica de 2M mensajes/segundo en un clúster de 3 brokers, con un margen de 18,000$\times$ respecto a la carga del piloto (0.11 msgs/s). La selección de compresión LZ4 equilibra reducción de tamaño (ratio 3.2:1) y overhead CPU (5\%), mientras que la configuración \texttt{acks=1} optimiza latencia (<50ms IEEE 2030.5) tolerando pérdidas ocasionales mediante el buffer de 7 días del TB Edge.
    
    \item \textbf{Optimización TimescaleDB:} La política de compresión columnar \texttt{AFTER 30 days} logra un ratio 10:1 (12 GB $\rightarrow$ 1.2 GB medidos en 90 días de telemetría de 192 dispositivos), mientras que las vistas materializadas (\emph{continuous aggregates}) reducen el tiempo de consulta de dashboards en un 95\% (queries sobre agregados horarios vs. escaneo de 2.88M registros crudos).
    
    \item \textbf{Rule Chains de negocio:} Se implementaron cuatro cadenas críticas (Procesamiento Telemetría, Gestión Alarmas, Facturación Energía, Exportación Datos) que automatizan la lógica completa del sistema AMI. La cadena de alarmas gestionó 23 eventos en el piloto (14 caídas de tensión, 6 sobre-temperatura, 3 sobre-corriente) con entrega 100\% de notificaciones y tiempo medio de reconocimiento de 18 minutos.
    
    \item \textbf{Costo operativo competitivo:} El despliegue AWS totaliza \$390/mes (\$2.03/dispositivo/mes para 192 medidores), significativamente menor a plataformas IoT gestionadas (\$10--15/dispositivo/mes) y con TCO similar a infraestructura on-premise durante el horizonte de 3 años del proyecto piloto.
\end{itemize}

La arquitectura presentada en este capítulo habilita la escalabilidad horizontal mediante particionado Kafka y réplicas de lectura PostgreSQL, permitiendo extensión a decenas de miles de dispositivos sin cambios arquitectónicos fundamentales.
