\section{Introducción}
\label{sec:server-intro}

El Nivel 4 arquitectura (capa central cloud) implementa plataforma IoT centralizada para gestión masiva dispositivos, analytics históricos, dashboards multi-tenant y APIs programáticas. Este capítulo documenta el despliegue de ThingsBoard 3.6.2 Community Edition en AWS con arquitectura microservicios, enfocando en tres pilares fundamentales:

\textbf{(1) Apache Kafka:} Sistema de mensajería distribuida para ingestión masiva datos. Kafka maneja concurrencia multi-device con throughput 10K msgs/s (100× margen piloto 192 devices), garantiza durabilidad mediante replicación broker (factor 2), y desacopla productores (Gateways Edge) de consumidores (Rule Engine, Analytics). Implementación con 3 brokers Kafka + 3 nodos Zookeeper + 8 topics particionados logra latencia P95 <50 ms ingesta E2E.

\textbf{(2) PostgreSQL + TimescaleDB:} Base datos híbrida relacionales + series temporales. PostgreSQL 15 almacena metadatos (devices, assets, users, relations) con esquema normalizado 42 tablas. TimescaleDB 2.13 extiende PostgreSQL con hypertables optimizadas para telemetría (particionado automático chunks 7 días, compresión columnar 10:1, continuous aggregates 5min/1h/1d). Retención policy 90 días telemetry raw, 365 días aggregates, DROP automático chunks obsoletos.

\textbf{(3) Rule Chains:} Motor lógica negocio ThingsBoard. Rule Chains procesan telemetría servidor con 4 chains críticas: (1) Root Chain (routing entrada), (2) Energy Billing Chain (cálculo facturación kWh × tarifa), (3) Alarm Processing Chain (clasificación severity CRITICAL/MAJOR/MINOR + notificaciones), (4) Analytics Chain (agregaciones históricas). JavaScript nodes ejecutan transformaciones custom, query Asset attributes para enriquecimiento contextual.

\textbf{Estructura capítulo:} §5.2 detalla infraestructura ingesta masiva (hardware servidor + arquitectura Kafka NUEVO 1500 palabras), §5.3 presenta despliegue ThingsBoard microservicios + optimización PostgreSQL/TimescaleDB (NUEVO 1000 palabras), §5.4 documenta lógica negocio Rule Chains (EXPANDIR 1200 palabras), §5.5 dashboards multi-tenant, §5.6 APIs/Webhooks, §5.7 conclusiones capítulo.

\subsection{Arquitectura Apache Kafka}
\label{sec:server-kafka}

Apache Kafka 3.5.1 es el sistema de mensajería distribuida core para ingesta masiva telemetría desde múltiples Gateways Edge. Kafka proporciona: (1) \textbf{Durabilidad} mediante replicación topics cross-broker (factor RF=2), (2) \textbf{Escalabilidad horizontal} particionando topics (8 partitions = 8 consumidores paralelos), (3) \textbf{Desacoplamiento} productores (Gateways) de consumidores (ThingsBoard Rule Engine), permitiendo procesamiento asíncrono sin bloquear ingesta.

\textbf{Componentes arquitectura Kafka:}

\begin{enumerate}
    \item \textbf{Kafka Brokers (2 nodos AWS MSK):}
    \begin{itemize}
        \item Broker IDs: kafka-01 (ID 1), kafka-02 (ID 2)
        \item Función: Almacenar particiones topics, servir produce/consume requests
        \item Persistencia: Logs disk-based (100 GB EBS gp3 por broker)
        \item Comunicación: Protocolo Kafka wire protocol TCP/9092 (interno VPC), TLS 9093 (externo)
    \end{itemize}
    
    \item \textbf{Zookeeper Ensemble (3 nodos managed MSK):}
    \begin{itemize}
        \item Función: Cluster coordination, broker discovery, leader election partitions
        \item Topología: 3 nodos quorum (tolera 1 fallo manteniendo quorum 2/3)
        \item Nota: Kafka 3.5 aún requiere Zookeeper (KRaft mode experimental, no production-ready)
    \end{itemize}
    
    \item \textbf{Schema Registry (Confluent, deshabilitado piloto):}
    \begin{itemize}
        \item Propósito: Versionado schemas Avro para compatibilidad backward/forward consumers
        \item Decisión: No implementado piloto (overhead innecesario 192 devices), JSON plain text suficiente
    \end{itemize}
\end{enumerate}

\textbf{Desglose topic crítico \texttt{tb.mqtt.telemetry}:}

\begin{itemize}
    \item \textbf{Partitions: 8} (distribución carga 8 consumidores paralelos ThingsBoard Rule Engine)
    \begin{itemize}
        \item Partition key: \texttt{hash(deviceId) mod 8} (garantiza telemetry mismo device siempre misma partition, orden preservado)
        \item Ejemplo: Device ESP32-C6-AB12CD \rightarrow hash(AB12CD) = 0x4F2A \rightarrow 0x4F2A mod 8 = \textbf{partition 2}
    \end{itemize}
    \item \textbf{Replication Factor (RF): 2}
    \begin{itemize}
        \item Cada partition tiene 1 leader + 1 follower replica en broker diferente
        \item Leader: Sirve produce/consume requests
        \item Follower: Sincroniza datos leader (async replication), promovido a leader si leader falla
        \item Durabilidad: Datos sobreviven fallo 1 broker (piloto tolera 1 de 2 brokers down)
    \end{itemize}
    \item \textbf{Retention: 7 días (168 horas)}
    \begin{itemize}
        \item Configuración: \texttt{retention.ms=604800000} (7 días en milisegundos)
        \item Tamaño estimado: 192 devices × 9,600 msgs/día × 320 bytes/msg × 7 días = 4.1 GB
        \item Cleanup: Kafka background thread borra segments obsoletos >7 días (log compaction disabled)
    \end{itemize}
    \item \textbf{Compresión: LZ4}
    \begin{itemize}
        \item Algoritmo: LZ4 (balance velocidad/ratio, 2.5× compresion JSON telemetry)
        \item Alternativas: gzip (mejor ratio 4× pero 3× más lento CPU), snappy (similar LZ4), none (sin compresión)
        \item Decisión: LZ4 seleccionado por latencia <5 ms compress/decompress vs 15 ms gzip
    \end{itemize}
\end{itemize}

\textbf{Consumer Groups y paralelismo:}

\begin{enumerate}
    \item \textbf{Consumer Group \texttt{tb-rule-engine-consumer}:}
    \begin{itemize}
        \item Función: Consume \texttt{tb.mqtt.telemetry}, ejecuta Rule Chains ThingsBoard
        \item Consumidores: 8 instancias paralelas (1 por partition)
        \item Balanceo: Kafka asigna automáticamente 1 partition por consumer (round-robin)
        \item Offset commit: Auto-commit cada 5s (\texttt{enable.auto.commit=true}, \texttt{auto.commit.interval.ms=5000})
        \item Tolerancia fallos: Si consumer crash, Kafka re-balancea partitions entre consumers supervivientes (rebalance protocol)
    \end{itemize}
    
    \item \textbf{Consumer Group \texttt{tb-telemetry-processor}:}
    \begin{itemize}
        \item Función: Consume \texttt{tb.mqtt.telemetry}, persistencia TimescaleDB (bypass Rule Engine para high-throughput)
        \item Consumidores: 4 instancias paralelas
        \item Decisión: Menos consumers que partitions (4 < 8) porque escritura DB es bottleneck, no CPU
    \end{itemize}
\end{enumerate}

\subsection{Balanceo de Carga y Rate Limiting}
\label{sec:server-balanceo}

\textbf{HAProxy Load Balancer para MQTT:}

AWS Application Load Balancer (ALB) maneja balanceo HTTP/HTTPS (dashboard ThingsBoard puerto 443), pero MQTT protocolo requiere balanceador TCP Layer-4. Implementación utiliza HAProxy 2.8 ejecutando en EC2 t3.small dedicado (2 vCPU, 2 GB RAM, \$30/mes).

\textbf{Configuración HAProxy (\texttt{/etc/haproxy/haproxy.cfg}):}

\begin{verbatim}
global
    maxconn 4096
    log /dev/log local0

defaults
    mode tcp
    timeout connect 5s
    timeout client 30s
    timeout server 30s

frontend mqtt_frontend
    bind *:8883 ssl crt /etc/haproxy/certs/server.pem
    default_backend mqtt_backend

backend mqtt_backend
    balance leastconn  # Algoritmo: Least connections
    option tcp-check
    tcp-check connect port 1883
    server tb-mqtt-01 10.0.1.10:1883 check inter 5s fall 3 rise 2
    server tb-mqtt-02 10.0.1.11:1883 check inter 5s fall 3 rise 2 backup
\end{verbatim}

\textbf{Características balanceo:}

\begin{itemize}
    \item \textbf{Algoritmo leastconn:} Rutea conexión MQTT nueva al backend con menos conexiones activas (óptimo para long-lived MQTT vs round-robin)
    \item \textbf{Health check TCP:} Valida puerto 1883 cada 5s, marca backend DOWN después 3 fallos consecutivos (fall 3), UP después 2 éxitos (rise 2)
    \item \textbf{Backup server:} tb-mqtt-02 solo recibe tráfico si tb-mqtt-01 falla (active-passive HA)
    \item \textbf{TLS termination:} HAProxy maneja handshake TLS, forward plaintext a backends (reduce carga CPU ThingsBoard)
\end{itemize}

\textbf{Rate Limiting multi-nivel:}

\begin{enumerate}
    \item \textbf{Per-device limit (HAProxy + ThingsBoard):}
    \begin{itemize}
        \item ThingsBoard Device Profile: Límite 100 msgs/s por device (configurable attribute \texttt{maxMsgsPerSecond})
        \item Implementación: Rate limiter token bucket (100 tokens/s capacity, burst 150 msgs permitido corto plazo)
        \item Acción exceso: HTTP 429 Too Many Requests (MQTT PUBACK failure), device debe implement exponential backoff
    \end{itemize}
    
    \item \textbf{Global limit (Kafka broker throttling):}
    \begin{itemize}
        \item Kafka broker config: \texttt{produce.purgatory.purge.interval.requests=10000}
        \item Límite: 10,000 produce requests/s agregado todos devices (89× margen piloto 112 msgs/s)
        \item Throttling mechanism: Kafka añade artificial delay produce response si excede quota
    \end{itemize}
    
    \item \textbf{CloudWatch Alarms:}
    \begin{itemize}
        \item Alarm: Telemetry rate >5,000 msgs/s sustained 5 min → SNS notification ops team
        \item Propósito: Detectar DDoS attack o misconfigured device flood
    \end{itemize}
\end{enumerate}

\textbf{Validación balanceo piloto:}

\begin{itemize}
    \item \textbf{Distribución carga:} tb-mqtt-01 recibió 68\% conexiones, tb-mqtt-02 (backup) 0\% (sin fallos tb-mqtt-01 durante piloto)
    \item \textbf{Failover test:} Simulado crash tb-mqtt-01 (kill -9 process), HAProxy detectó DOWN en 15s (3× health check 5s), promovió tb-mqtt-02 a active, reconexión MQTT devices automática 18-24s promedio
    \item \textbf{Rate limiting:} 0 devices excedieron 100 msgs/s limit (telemetry 15 min interval = 0.001 msgs/s, 100,000× margen)
\end{itemize}
